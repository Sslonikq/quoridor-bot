### Капы при переиспользовании (главный вопрос)
Корректно:
- Поддерево переиспользуется только при `nodes + 2 <= MAX_NODES` и `edges + 1024 <= MAX_EDGES`. Новые массивы `min(cap, max(X0, 2·size))` не меньше `nodes` / `edges`, так что `mcts_compact` (без проверки границ, очередь размером `dn.size`) пишет в пределах массивов.
- Корневые добавки (`_jit_write_edges`) требуют `ctr[1] + len(moves) + 256`; `len(moves) <= MAX_MOVES = 256`, итого ≤ 512 < 1024. Если массив рёбер меньше, `grow()` удваивает до капа, а запас 1024 под капом гарантирует, что `MemoryError` не возникнет.
- Порог `+256` в `grow()` совпадает с `MAX_MOVES` в условии `ST_FULL` ядра (kernels.py:1483), зацикливания «ST_FULL → grow без изменений» нет.
- Ветка «не переиспользовать» обнуляет `ctr` и использует уже выделенные массивы (≤ капов): новой памяти нет.
- Ядро py капов не имеет; расхождение py/jit возможно только у дерева, упёршегося в капы, чего в партиях ботов не бывает (0093, п. 1). Тесты jit == py по партиям с переиспользованием проходят.

### Решатель
- `STACK = MAX_PLY + 2` = размер стека `_JitCore`, проверка `r` в `eg_search` (min строк всех пяти буферов) и в `_PyCore.root` одинакова; `MAX_DEPTH = 160 < STACK`. Тест на обоих ядрах, включая граничную строку `STACK - 1`.
