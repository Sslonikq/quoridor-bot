# 0061 · Бот v4: анализатор на полном бюджете, оценка гонки стенок, PVS + LMR, практичная игра в проигрыше

- **Дата:** 2026-10-16
- **Агент:** ai-engineer
- **Статус:** partial. Сила: v4 сильнее v3, 800 партий. Глубина анализатора равна глубине SearchBot. Критерии game02/game03 по оценке **не выполнены**, см. «Проблемы».
- **Связанные отчёты:** 0037, 0038, 0053, 0057, 0059, 0060

## Задача
Фаза 8, пункты 1–5. (1) Лучший ход в анализаторе должен считаться одним обычным поиском на весь бюджет, глубина на 3 с должна совпадать с SearchBot. (2) Оценка v4: ценность стенки в запасе по её реальной пользе и эндшпиль при 0 стенок у соперника. (3) Сопротивление в проигранной позиции (game03, ходы 21–33). (4) v4, v4-clock, v4-0.2s в реестре; v4 по умолчанию в cli и анализаторе. (5) Матч v4 против v3 при равном времени, не меньше 200 партий.

## Базовая линия (до шага)
- v3, 0.2 с на ход, 80 позиций из партий самоигры (40 эндшпильных, где стенки только у одной стороны, и 40 миттельшпильных): эндшпиль 69.5k nodes/s, средняя глубина 10.95; миттельшпиль 34.6k nodes/s, глубина 6.80.
- Анализатор против SearchBot (v3, `move_time=3`, без лимита глубины), 31 позиция game01–03 (каждый 6-й полуход): средняя глубина 12.00 против 11.97. В двух позициях SearchBot глубже на 1 (g2:14 — 9 против 8, g3:26 — 14 против 13). Причина: главный поиск анализатора получал 80% бюджета (2.4 с). Новую итерацию он не начинает после половины своего бюджета, то есть после 1.2 с, а SearchBot — после 1.5 с.
- v3 с двойным временем (0.4 с против 0.2 с): 245/154/1, 61.4%. Это мерка ценности ускорения.

## Что сделано
1. **Анализатор (`search_top`).** Главный поиск теперь получает **весь** `time_limit`, ровно как SearchBot. Альтернативы топ-2/3 досчитываются в остатке бюджета, но не меньше `alt_share` = 0.1 от него. Вся подсказка укладывается примерно в `time_limit × 1.1`. `engine.ALT_SHARE` = 0.1. Глубина уже отдаётся в `/api/analyze` и выводится в интерфейсе («гл. N» в топе, «Глубина N» в строке статуса); статику не трогал, кроме подписи «бота v4».
2. **Оценка v4 (`eval.evaluate_v4`, `Searcher.wall_race`).** Пока стенки есть у обеих сторон, оценка такая же, как в v3. Если стенки остались только у стороны A:
   - строится жадный план A: на каждом шаге ставится стенка, сильнее всего удлиняющая путь B, пока она добавляет хотя бы 2 шага. Стенка стоит A один ход, поэтому +1 ничего не даёт;
   - к оценке v3 добавляется `PLAN_V4` = 50 за шаг чистого выигрыша плана (Σ(gain − 1));
   - если гонку A выигрывает только благодаря плану, добавляется `SOFT_V4` = 425;
   - если A выигрывает чистую гонку, план не считается (решает RACE, как в v3).

   Веса взяты из логистической регрессии по 260 712 позициям из 4000 партий самоигры v3 на глубине 4: log-loss на отложенной выборке 0.5191 → 0.5139. Ускорения:
   - кандидаты B-стороны берутся только из «узких» слоёв кратчайших путей (новая `bitpaths.shortest_layers`: стенка удлиняет путь, только если перекрывает все рёбра между двумя соседними слоями, а в них не больше двух клеток);
   - таблица стенок по рёбрам без объектов WallMove;
   - кеш плана по (стенки, клетка B), фишка A не учитывается;
   - симметричный по цвету тай-брейк.
3. **Поиск: PVS + LMR (только v4).** После первого хода — нулевое окно, в том числе в корне; при fail-high — пересчёт. С третьего хода (индекс ≥ 3) при оставшейся глубине ≥ 3 поиск на 1 полуход мельче, при fail-high — пересчёт на полную глубину. PVS без LMR даёт те же оценки, что и без него (тест).
4. **Проигранная позиция (`delay_slack` = 2, `_practical_loss`, только v4).** Оставляем кандидатов, которые проигрывают не более чем на 2 полухода быстрее самого позднего проигрыша. Среди них выбираем по порядку:
   1. стенку, сильнее всего удлиняющую путь соперника;
   2. ход с наибольшей разностью путей (соперник − свой), то есть продвижение без отступлений;
   3. самый поздний проигрыш.

   v3 (`delay_slack=0`) не изменился.
5. **Реестр и умолчания.** `V4_SETTINGS`, боты `v4` (глубина 3), `v4-clock`, `v4-0.2s`. `cli --bot` по умолчанию `v4`. Анализатор (`_CancellableSearcher`) работает на `V4_SETTINGS`. У `SearchBot` новые параметры `v4`, `pvs`, `lmr`, `delay_slack`; с `searcher=` они запрещены, как и остальные.

## Решения и почему
- **Отвергнутые варианты оценки** (всё измерено матчами):
  - «Мёртвые» стенки (после плана ни одна стенка не удлиняет путь B) дешевле запаса: вес 60 давал 46.8% против v4 без этого при 0.2 с и **42.1% при 1 с** (190 партий); вес 20 — 45.6%.
  - Остаток стенок по 10/60/100 вместо оценки v3: 36–38%. Скачок оценки, когда соперник тратит последнюю стенку, заставляет обе стороны спешить её потратить.
  - Веса по фазе из регрессии (шаг дешевле при многих стенках, стенка дороже при длинных путях; log-loss 0.5024): на глубине 4, 760 партий — 53.1% / 46.0%, шум или хуже.
  - LMR с индекса 2 / 5: 47.2% / 44.4% против lmr=3; редукция на 2 полухода с индекса 6 / 8: 46.0% / 49.8%.

  Данные самоигры прямо показывают, почему обесценивание проигрывает. В позициях, где у A после плана гонка проиграна на 1–3 хода, а стенок осталось 3–5, A всё равно выигрывает 45–80% партий; с 6+ стенками — 85–100%, даже если сейчас ни одна стенка не удлиняет путь B. При поиске на 7–10 полуходов запас стенок реализуется: комбинации из 2+ стенок, новые узкие места по мере хода B.
- **Ошибка, найденная по пути:** в одной из версий `evaluate_v4` при 0 стенок у обоих потерялось `−RACE` для стороны, проигрывающей гонку. Тест «v4 = v3 вне гонки» её поймал. Все матчи с этой версией отброшены, а фоновые процессы с ней остановлены по PID.
- **Фишка A не учитывается в плане:** кеш по (стенки, клетка B) поднял скорость эндшпиля с ~26k до ~35k nodes/s. Цена: план не видит, что стенка удлиняет и путь самого A (общий коридор, как в game03).
- **delay_slack = 2:** продвижение и удлиняющие стенки важнее проигрыша ровно на 1 ход. Это для игры против человека; в матчах ботов проигранные позиции решены заранее.

## Breaking changes
- `Searcher.search_top`: главный поиск получает весь `time_limit` (было `× (1 − alt_share)`); `alt_share` по умолчанию 0.1 и теперь означает минимальную долю для альтернатив. Подсказка может идти до ~1.1 × бюджета.
- `engine.ALT_SHARE` 0.2 → 0.1; анализатор считает ботом v4.
- `cli --bot` по умолчанию `v4` (было `v3`).
- Новые необязательные параметры у `Searcher` и `SearchBot`; поведение v1–v3 не изменилось.

## Проблемы и открытые вопросы
- **Критерии game02/game03 не выполнены** (v4, 3 с):
  - game02, ход 20: топ-1 `f2h` (не f2), но **f2 второй** с той же оценкой +4.25. xfail `test_game02_move_20_f2_is_not_in_the_top_known_limit` оставлен.
  - game03, ходы 11–16: лучший ход везде пешечный (c2, d2, e2, e2, f2, g2), стенки на 2–3 месте. Ходы 8–12 game02: стенка первой на ходах 9, 11, 12.
  - game03, ход 16 (g2): при 4 с и 20 с одинаково **+4.75**, то есть стабильно, но неверно: v3 за 30 с (глубина 33) даёт −9.0, после 16…g3h мат за 36 полуходов. Причина — общий коридор: стенки белых удлиняют и путь самих белых, а запас из 7 стенок оценка считает по 125. Обесценивание таких стенок исправило бы эти позиции, но проигрывает матчи (см. выше).
- game03, ходы 21–33: позиция проиграна при любой игре. «Туда-обратно» — это отступление перед фишкой соперника в общем коридоре: шаг вперёд даёт чёрным прыжок и проигрывает на 3 хода (6 полуходов) быстрее, больше допуска. Стенки белых там мёртвые (ни одна не удлиняет путь чёрных). v4 выбирает то же, но теперь при равной скорости проигрыша предпочитает удлиняющие стенки и продвижение.
- **CLAUDE.md не правил**: агенту запрещено менять его по сообщению другого агента. Пользователю нужно обновить строку с реестром ботов: добавить `v4, v4-clock, v4-0.2s (v3 + оценка гонки стенок + PVS/LMR; по умолчанию в cli и анализаторе)`, а у v3 убрать пометку «по умолчанию в cli».
