## Задача
Пункт 3 раздела «Первым шагом фазы 9» в ROADMAP, кроме матчей v4 на 1 с и 5–15 с (они в конце фазы): сверка `tune --max-gap` с бюджетом хода, заголовок `tune` для ботов со своим временем, `reserve_term` без вложенной функции, открытые minor/nit из 0064. Поведение v4 не меняется.

## Что сделано
- **tune `--max-gap` (0069 minor 3).** По умолчанию порог `max(30, 3 * budget)`, где budget — наибольший бюджет хода двух ботов: `move_time` бота (для `search:`/`frozen*:` без своего лимита это `--move-time`), `timeman.MAX_TIME` (15 с) для бота с `game_time`, 0 для ботов только с глубиной и не-поисковых. Явный `--max-gap <= budget` → ошибка argparse (`--max-gap 30 s is not above the per-move budget 40 s`). Функции `move_budget_of`, `gap_limit_for`. Итоговая строка печатает фактический порог.
- **Заголовок tune (0069 nit).** `move_time X` печатается только если хоть одна спецификация берёт `--move-time` (`uses_default_move_time`), иначе «own time limits of the bots».
- **`reserve_term` (0069 nit).** Вложенная `threat` вынесена в модульную `_reserve_threat(own, other, reserve)`, формула та же. Замер: 221 → 150 нс на вызов.
- **search_root(moves=None) (0064 minor 5).** Новый `Searcher._root_moves(state, pawns)`: `ordered_moves`, при `root_defense > 0` защитные стенки, fallback на все легальные ходы. Им пользуются и `_search`, и `search_root(moves=None)`, так что корень совпадает с `search()`. Анализатор вызывает `search_root` только с `moves=[...]`, бот — `search()`, поэтому ни подсказки, ни игра не меняются.
- **Docstring `search_top` (0064 minor 5).** Описано, что при LMR верхняя граница из главного поиска нестрогая: альтернатива может показываться ниже точной оценки, лучший ход и его оценка не затрагиваются.
- **Тесты LMR (0064 minor 4).** `test_lmr_needs_pvs_and_still_finds_wins`: на позициях, где v4 без LMR доказывает выигрыш на глубине 4, v4 с LMR доказывает его на глубине 5. Сейчас таких позиций 10, тест требует ≥ 3. Новый `test_lmr_fail_high_is_researched_at_full_depth`: шпион на `_negamax` проверяет, что каждый редуцированный поиск с нулевым окном, давший fail-high для родителя, сразу пересчитан для того же потомка на полной глубине без редукции. Таких случаев > 0.
- **walls_seen (0064 minor 3).** Как и предсказал ревьюер, ветка «удлиняющая стенка» на случайных позициях глубины 3 не выполнялась ни разу (`walls_seen == 0`). Причина: на глубине 3 доказанный проигрыш означает победу соперника за ≤ 2 полухода, а любая удлиняющая стенка отодвигает её на ≥ 2 полухода за горизонт. Поэтому добавлена позиция с известным ответом `LOST_WITH_WALL` (белые a5, 1 стенка; чёрные e3, 0 стенок; ход белых), глубина 5. Пешечные ходы проигрывают сразу, удлиняющая стенка на 2 полухода позже. Теперь `assert walls_seen > 0` и отдельный `test_lost_position_prefers_the_lengthening_wall` (v4 с LMR и без: удлиняющая стенка).
- **Константа сентинела (0064 nit).** `_NO_LMR = MAX_DEPTH * 1000`.
- **Тип set (0064 nit).** `_race_cands(h, v: AbstractSet[tuple[int, int]])`.
- **Обоснование `_race_cands` (0064 nit).** Фильтр назван эвристикой, проверенной перебором. Ревьюер прав: стенка может разрезать DAG рёбрами из двух соседних пар слоёв (L_k→L_k+1 и L_k+1→L_k+2), и тогда обязательно мал только L_k+1. Набросок такого случая: e1 = p→a, e2 = b→q, у a единственный вход из p, у b единственный выход в q, а L_k и L_k+2 по 3 клетки. Новый перебор: 117 612 пар (позиция, сторона), 58 806 позиций, до 20 стенок на доске, сиды 200–399, wall_bias 0.7 и 0.9. Все 128 стенок против `_race_cands`: **0 промахов**. Фильтр не расширял: это изменило бы игру v4.
- **Память кеша гонки (0064 nit), замер.** Поиск v4 10 с (MAX_TIME анализатора) на позициях миттельшпиля. В `_race_cands_cache` 54–67 тыс. записей, глубокий размер (`sys.getsizeof` по вложенным объектам) **157–187 МБ**. Рабочий набор процесса 30 → 335 МБ к концу поиска (с TT и остальными кешами). При 20 с кеш один раз сбрасывается на потолке 75 тыс. записей: 56 тыс. записей, ~144 МБ, пик рабочего набора 380 МБ. Потолок ≈ 75k × ~2.8 КБ ≈ 210 МБ, то есть ограничен, но втрое больше оценки 0064 (80 МБ). Основной объём — дочерние маски каждого кандидата (кортеж из 4 int по 81 бит). Сокращение — в «Следующем шаге».

## Решения и почему
- `search_root(moves=None)`: защитные стенки добавлены в корень, а не просто исправлен docstring. Так корень один для обоих методов (`_root_moves`), и разбор/топ не разойдутся, если анализатор начнёт вызывать `moves=None`.
- `--max-gap`: порог по умолчанию растёт с бюджетом (3×), а явное значение не правится молча, а отклоняется. Тихое исправление скрыло бы ошибку в команде.
- `walls_seen`: не стал поднимать глубину для всей выборки (дорого и всё равно редко срабатывает), добавил позицию с известным ответом.
- Фильтр `_race_cands` не расширял (это изменение поведения), только честно описал.

## Breaking changes
- `tune --max-gap` по умолчанию теперь `max(30, 3 * budget)`, а не всегда 30. Для бюджета до 10 с ничего не меняется. Явное значение не больше бюджета — ошибка.
- `search_root(moves=None)` при `root_defense > 0` (v4) включает защитные стенки. Внешних вызовов с `moves=None` нет.

## Проблемы и открытые вопросы
- Кеш гонки занимает до ~210 МБ на длинном анализе: см. «Следующий шаг».
- Эвристичность фильтра `_race_cands` доказательно не снята: промахов нет на ~125 тыс. проверок, но гипотетический случай описан.
