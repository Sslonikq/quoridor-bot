## Задача
Фаза 7: локальный анализатор `python -m quoridor.analyzer`: доска, ходы за обе стороны, подсказки бота v3 (топ-3 с оценкой и «почему», стрелка/зелёная стенка, шкала оценки), всё офлайн, правила только на сервере.

## Что сделано
- `engine.py`: проигрывание списка ходов от начальной позиции через `notation.parse_move` + `rules.apply_move` (`MoveListError` с номером нелегального хода), JSON позиции (фишки, стенки, запас, чей ход, победитель, длины путей, все легальные ходы в нотации), ранжирование корневых ходов.
- `server.py`: `ThreadingHTTPServer` на `127.0.0.1`, порт 0; `POST /api/state`, `POST /api/analyze`; статика только из белого списка (`/`, `/app.js`, `/app.css`); проверка `Host`/`Origin` (защита от DNS rebinding), лимит тела 64 КБ, ошибки HTTP 400 `{ok:false, error, bad_move}`. Новый `/api/analyze` отменяет предыдущий (старый отвечает `{ok:true, cancelled:true}`).
- `__main__.py`: `--port`, `--no-browser`; открывает браузер, Ctrl+C завершает сервер.
- `static/`: `index.html` + `app.css` + `app.js` по макету (без CDN и внешних шрифтов): клик по клетке, призрак стенки (красный с ✕ для нелегальной), отмена (Backspace), переворот (F), подсказка вкл/выкл (H; при выключении расчёт не запускается и отменяется), шкала оценки, топ-3 кликабельны (делают ход), список ходов, «Копировать ходы», «Новая доска». Победа: ходы блокируются.
- Топ-3: у `search.py` нет API «оценки всех корневых ходов», поэтому `rank_moves` берёт корневые ходы через публичный `Searcher.ordered_moves` (ходы фишкой + отобранные стенки) и ищет каждого ребёнка полным окном `Searcher.search(child, depth)` с итеративным углублением (глубина k, пока хватает бюджета; недозавершённая итерация отбрасывается, чтобы оценки были сравнимы). Параметры v3: `tt_bits=V2_TT_BITS`, `wall_weight=V3_WALL_WEIGHT`. Подкласс `Searcher` переопределяет публичный `evaluate`, чтобы быстро прервать расчёт при отмене. Выигрыш на месте возвращается сразу.
- Оценки отдаются с точки зрения белых в сотых шага; `|score| >= 900000` на клиенте показывается как «Б+∞/Ч+∞».

## Решения и почему
- Анализ синхронный на запрос: поток обработчика считает, отмена через `threading.Event`; клиент ещё и делает `AbortController.abort()`. Отдельный процесс не нужен: отмена укладывается в доли секунды благодаря проверке в `evaluate`.
- Клиент знает геометрию нотации (где рисовать стенку), но не правила: легальность, пути, победитель, список легальных ходов приходят с сервера. Перед ходом клиент сверяется с `legal`, а сервер всё равно перепроверяет весь список.
- Топ-3 считается своим циклом по корню, а не изменением `search.py` (запрещено трогать).
- В фазе 7 не делал: график, загрузку партии, листание, разметку (фаза 8), компактный режим и 📌 (фаза 9).

## Проблемы и открытые вопросы
- (ai-engineer) Для топ-N нужен публичный `Searcher.search_root(state, depth, ...)`, возвращающий оценки всех корневых ходов с общим окном и TT: сейчас каждый ребёнок ищется отдельно, это медленнее и без сквозной TT. Сейчас глубина за 2 с: 5–8 (в сложных позициях 5).
- (ai-engineer) Оценка на чётной/нечётной глубине «качается» (начальная позиция −1.0 при глубине 7, 0.0 при 8): шкала на старте может показывать ±1 шаг. Стоит сглаживать (оценка по двум последним глубинам) или документировать.
- Корневой набор стенок обрезан (`wall_limit`), поэтому ход пользователя может не входить в топ; для разбора партии (фаза 8) нужно отдельно оценивать сыгранный ход (`search` по ребёнку без отбора).
- Нет автотеста запуска `python -m quoridor.analyzer` как подпроцесса (проверен вручную).
- Страница при узком окне прокручивается (зазор под доской); косметика для фазы 9.
