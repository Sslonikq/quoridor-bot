- **Дата:** 2026-10-15
- **Агент:** ai-engineer
- **Статус:** done (проверка game02 на ходах 19–20 выполнена частично: см. «Проблемы»)
- **Связанные отчёты:** 0045, 0048, 0051, 0052

## Задача
Первый шаг фазы 8, п. 2 (ROADMAP): публичный `Searcher.search_root`. Анализатор считал мелко, потому что `rank_moves` делил бюджет между всеми корневыми ходами: за 2 с глубина 7–12, а SearchBot за то же время доходит до 9–19. Кроме того, сделано: лучший ход в проигранной позиции, сглаживание качания оценки по чётности глубины и оценка заданного (сыгранного) хода.

## Что сделано
- `search.py`:
  - `search_root(state, max_depth, time_limit, moves=None, top=None) -> RootSearch`. Оценивает все корневые ходы итеративным углублением с одним общим окном и одной TT. Окно: alpha = top-я лучшая точная оценка текущей итерации. При `top=None` все оценки точные, при `top=k` точные только лучшие k, остальные верхние границы (так дешевле). `moves=[...]` позволяет оценить любые легальные ходы, включая стенку вне отбора `wall_limit`; для нелегального хода ValueError.
  - `search_top(state, time_limit, top_n=3, alt_share=0.2) -> TopResult`. Сначала обычный `_search` (тот же, что в `search()`/SearchBot) получает 80% бюджета. Затем `_root_scores` остальных корневых ходов с `top=top_n-1` получает остаток времени, но не меньше 20%. Он использует TT и кеши основного поиска и идёт не глубже основного. Оценки альтернатив ограничены сверху оценкой лучшего хода и верхней границей, которую основной поиск доказал для этого хода на своей глубине.
  - Проигранная позиция (лучшая оценка = доказанный проигрыш): `_delay_loss`. Кандидаты: все корневые ходы плюс все легальные стенки, удлиняющие путь соперника, без фильтра gain и без `wall_limit` (`_lengthening_walls`). Каждого кандидата проверяем null-window на той же глубине. Ходы, проигрывающие быстрее, отбрасываются. Из остальных выбирается ход с самым поздним проигрышем (стенка вне отбора может вообще не проигрывать, тогда считается её точная оценка). Дальше по порядку: максимум разности путей (соперник − свой), путь соперника, сидовый порядок. Это работает и в SearchBot, и в анализаторе (код общий).
  - `display_score(score, depth)` и `SearchResult.display_score`: ±`TEMPO` = 50 (полшага) в зависимости от чётности глубины. Это компенсирует темп стороны, которая ходит в листе. Используется только для показа, на поиск не влияет.
  - Рефакторинг: `_reset` / `_free` / `_keys` / `_check_args`. `_search` больше не сбрасывает кеши, поэтому `search_top` переиспользует TT между фазами.
- `analyzer/engine.py`:
  - `rank_moves` переписан на `search_top`. Глубина в ответе теперь равна глубине лучшего хода (как у SearchBot), отсчёт от корня.
  - `DEFAULT_TIME = 3.0`, `ALT_SHARE = 0.2`.
  - У каждого элемента `top` новые поля `depth` и `exact` (`exact=false` значит верхняя граница). Оценки в топе берутся через display_score.
  - Новый API `evaluate_move(moves, move, seconds, cancelled)`: оценка одного заданного хода на весь бюджет через `search_root(moves=[mv])`. Для нелегального хода или законченной партии MoveListError с `number`.
- `analyzer/server.py`: только docstring (`time` по умолчанию 3.0, поле depth). Маршрут для `evaluate_move` не добавлялся, это задача ui-engineer в фазе 8.
- Тесты: `tests/search/test_search_root.py` (13 новых), `tests/analyzer/test_engine.py` (+5 быстрых, +4 slow на game02), `tests/analyzer/test_server.py` (+1 slow: подсказка без `time`, то есть 3 с, укладывается в ≤ 3.5 с, глубина есть в ответе).

## Качание оценки по чётности
Замер на фиксированной глубине, лучший счёт в центишагах:

| позиция | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|
| старт+e2e8 | 100 | 0 | 100 | −100 | 0 | −100 |
| g1:30 | 0 | −100 | 0 | −100 | 0 | −100 |
| g2:36 | 500 | 400 | 500 | 400 | 500 | 400 |

Причина: статическая оценка не учитывает темп стороны, которая ходит в листе. Сглаживание ±50 в зависимости от чётности (display_score) даёт 450 на всех глубинах для g2:36 и 50/−50 вместо 100/0/−100 для старта. Выбор хода не меняется: на фиксированной глубине сдвиг одинаков для всех листьев. Поэтому силу это не теряет. В eval.py сдвиг не вносился: v3 не изменён.

## Решения и почему
- «Общее окно» = окно multi-PV: alpha равна k-й точной оценке. При k = числу ходов все оценки точные; это и есть `search_root` для разбора партии. Для топа анализатора k=2: это дешевле и даёт точные оценки как раз для показа.
- Главный ход получает 80% бюджета, а не 100%: так требование «≤ бюджета» сохраняется для всей подсказки. Сам поиск тот же, что у SearchBot (тест `test_search_top_best_move_is_exactly_search`: ход, оценка и глубина совпадают на фиксированной глубине).
- Оценки альтернатив не выше лучшей: альтернативы считаются на меньшей глубине, и без потолка вторая строка могла бы показать больше первой. Верхняя граница из основного поиска понижает альтернативы, которые основной поиск уже опроверг (в том числе до проигрыша).
- В проигранной позиции поиск расширен на все удлиняющие стенки. Отбор `wall_limit`/gain рассчитан на нормальные позиции; при проигрыше стенка с gain ≤ 0 может оказаться лучшей защитой. На выбор вне проигранных позиций это не влияет.
