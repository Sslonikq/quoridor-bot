# Quoridor Bot

Бот для игры «Коридор» (Quoridor), 2 игрока, доска 9×9.
Цель: сильный и быстрый движок, укладывающийся в контроль времени 10 минут на партию.

## Фазы
План и текущая фаза: `ROADMAP.md`. Читай его в начале работы, делай только задачи текущей фазы.
`README.md` не трогать до последней фазы.

## Ограничения
- **Полностью офлайн.** Никаких сетевых запросов в рантайме: ни API, ни телеметрии, ни автообновлений, ни загрузки моделей. Зависимости ставятся один раз через pip.
- Подсказки на экране предназначены для дружеских партий, где соперник в курсе.

## Стек
- Python 3.11+, `pytest`, `ruff` (линт + формат).
- Без внешних игровых библиотек: правила пишем сами.
- Если скорости Python не хватит, горячие места переносим (numba / Rust через pyo3), но только после профилирования.

## Команды
```bash
pytest -q                 # все тесты
pytest tests/rules -q     # только правила
ruff check . && ruff format .
python -m quoridor.cli    # играть против бота в консоли
python -m quoridor.arena --games 100 --a v2 --b v1   # матч версий бота
```

## Правила (источник истины)
- Доска 9×9, колонки `a`–`i` (слева направо), ряды `1`–`9` (снизу вверх).
- Белые стартуют на `e1` и идут к ряду 9, чёрные стартуют на `e9` и идут к ряду 1. Первыми ходят белые.
- У каждого 10 стенок. Стенка длиной 2 клетки ставится в паз между клетками.
- Ход: **либо** шаг фишкой, **либо** постановка стенки.
- Шаг: на 1 клетку по ортогонали, если между клетками нет стенки.
- Прыжок: если соседняя клетка занята соперником, можно перепрыгнуть его по прямой.
  Если за соперником стенка или край доски, можно уйти по диагонали (влево или вправо от него), если это не перекрыто стенкой.
- Стенка нелегальна, если она:
  1. выходит за доску;
  2. перекрывает существующую стенку (даже частично) **или** крестом пересекает её в том же центре;
  3. отрезает **любого** игрока от его финишного ряда (проверка BFS/A*).
- Победа: фишка достигла финишного ряда.

## Нотация (как на сайте)
- Ход фишкой: клетка назначения, например `e2`.
- Стенка: клетка-якорь + ориентация, например `e3h` / `f3v`.
- Нотация стенок подтверждена по скриншотам: якорь — **верхняя левая клетка квадрата 2×2**.
  `a4h` — горизонтальная стенка между рядами 4 и 3, закрывает колонки a и b;
  `a2v` — вертикальная между колонками a и b, закрывает ряды 2 и 1.
  Якорь допустим только в колонках a–h и рядах 2–9.
- Вся конвертация живёт в одном модуле `quoridor/notation.py` и покрыта тестами.
  Не размазывать знание о нотации по коду.

## Архитектура
```
quoridor/
  state.py      # неизменяемое состояние: позиции, стенки (битборды/множества), счётчики, чей ход
  rules.py      # генерация легальных ходов, применение хода, проверка победы
  paths.py      # кратчайшие пути (BFS), кеширование
  notation.py   # строка <-> Move, единственное место, знающее формат сайта
  eval.py       # оценочная функция
  search.py     # поиск (alpha-beta + iterative deepening; MCTS как альтернатива)
  timeman.py    # распределение времени на ход
  cli.py, arena.py
  vision/       # захват экрана (mss), распознавание доски (OpenCV), калибровка
  overlay/      # прозрачное окно поверх доски с подсказкой, горячие клавиши
tests/
  rules/ paths/ notation/ search/ vision/
  fixtures/screens/  # скриншоты доски с известной позицией для тестов распознавания
reports/        # отчёты о проделанной работе (см. ниже)
```

## Принципы
- Правила важнее силы бота: сначала 100% корректная генерация ходов, потом поиск.
- Любой баг в правилах сначала фиксируем падающим тестом, потом чиним.
- `rules.py` и `paths.py` чистые и детерминированные: без I/O, без глобального состояния.
- Оптимизация только с замером «до/после» (время на позицию, nodes/sec) в отчёте.
- Изменение силы бота подтверждаем матчем в `arena` (минимум 100 партий), результат пишем в отчёт.

## Отчёты: ОБЯЗАТЕЛЬНО
После **каждого** завершённого шага (фича, фикс, рефакторинг, эксперимент), будь то основная сессия или любой агент:
1. Создай файл `reports/NNNN-YYYY-MM-DD-<agent>-<slug>.md`, где `NNNN` = следующий свободный номер (смотри `ls reports`).
2. Заполни его по шаблону `reports/_TEMPLATE.md`.
3. Не редактируй старые отчёты. Если что-то исправлено позже, пиши новый отчёт со ссылкой на старый.
4. Шаг не считается завершённым, пока нет отчёта, не проходят тесты и пользователю не выведены команды git (см. ниже).

## Git: коммиты делает пользователь
- **Никогда** не выполняй `git add`, `git commit`, `git push`, `git reset`, `git checkout` и т.п. Только чтение: `git status`, `git diff`, `git log`.
- В конце каждого шага (после отчёта) выведи пользователю готовые команды, явно перечислив файлы (без `git add .`):
  ```
  git add quoridor/rules.py tests/rules/test_jumps.py reports/0002-2026-10-14-rules-engineer-jumps.md
  git commit -m "feat(rules): прыжки и диагональные ходы" -m "- прыжок через соперника по прямой" -m "- диагональ, если за соперником стенка или край" -m "- 14 тестов на edge cases"
  ```
- Отчёт шага всегда входит в список файлов.
- Заголовок коммита: `<тип>(<область>): <что сделано>`, до 72 символов. Типы: `feat`, `fix`, `test`, `refactor`, `perf`, `docs`, `chore`. Области: `rules`, `paths`, `notation`, `eval`, `search`, `vision`, `overlay`, `arena`, `cli`, `agents`.
- Тело: по одному `-m` на пункт, что сделано и зачем.
- Если в одном шаге несколько независимых изменений, предложи несколько коммитов по очереди.
- Команды под Windows PowerShell; пути с пробелами в кавычках.

## Агенты (`.claude/agents/`)
| Агент | Когда звать |
|---|---|
| `rules-engineer` | состояние, генерация ходов, стенки, пути, нотация |
| `ai-engineer` | оценка, поиск, тайм-менеджмент, производительность |
| `test-engineer` | тесты, edge cases, регрессии, матчи в arena |
| `vision-engineer` | захват экрана, распознавание доски, оверлей |
| `code-reviewer` | ревью перед коммитом (только чтение) |

Типовой цикл: `rules-engineer`/`ai-engineer` → `test-engineer` → `code-reviewer`.
